2. HOW A TOOL RESULT REACHES THE USER (frontend_backend_agent/src/tool_handlers.py)
 The backend (Thinker, Super VL reasoning on) only PLANS the tool call. It does
 not write the spoken answer. The tool runs and Python formatters
 (result_formatters.py) build a short TTS-safe response_text. Delivery then
 depends on the mode (_deliver_tool_payload / _should_deliver_directly):
 Generic assistant (English), default mode "direct" (generic/backend.py):
   - response_text is pushed straight into TTS (_emit_talker_response); the
     Talker does not rephrase it.
   - Exception: get_weather is in talker_result_tools. The Talker gets a trimmed
     fact set (city, temperature, unit, condition, feels_like, humidity, wind)
     and writes the sentence itself (run_llm=True).
   - Non-speakable payloads (errors, needs-input) are not read verbatim; they go
     to the Talker as the tool result and it decides what to say.
 Multilingual assistant (language locked, Hindi preset or picked language):
   - pipeline.py forces force_tool_result_mode="talker", overriding the direct
     default and the env switches, because response_text is an English template.
   - For EVERY tool the Talker (Bolt by default) receives _talker_result_
     projection: response_text (English facts), status, and reply_language plus
     reply_instruction ("say this only in <language>, native script, keep every
     number/name/unit exact, never read the English aloud").
   - Guards behind it: a reply not in the session language, or one that only
     repeats the spoken filler, is retried; last resort is the result text
     translated to the session language (never needed in the Hindi SQA run 6).
 Filler: in both agents the Talker also speaks a short filler before the tool
   returns ("एक पल रुकिए..." in Hindi); that is separate from the final answer.
 Not traced: whether any tool (e.g. web_search) calls a model to summarise.

B. BUILDER DESIGN
 Transport (same pattern as the voice agent today):
   The browser never holds a key. Today nginx in the Astra UI pod
   (docker/nginx-nvcf.conf.template) injects NVIDIA_API_KEY + function-id,
   both from Vault (external secret fusion/astra/nemotron-voice-agent-astra/
   nemotron-voice-agent-deploy/stg), and the browser calls same-origin paths.
   The builder uses the same model: browser -> same-origin /builder/* -> builder
   service -> standalone Super VL NIM function
   https://91010bab-6b8c-4aca-8944-0f647a8069b2.invocation.api.nvcf.nvidia.com/v1/chat/completions
   Check first: whether the Vault NVIDIA_API_KEY may invoke 91010bab (keys can be
   function-scoped; it was tested only with NVCF_API_KEY). Else widen scope or add
   a second Vault secret.
 Why a builder service, not a plain nginx proxy: nginx can only lock path,
   method, body size and rate; it cannot enforce the system prompt, max_tokens
   or the schema, so a plain proxy would be an open chat endpoint on our key.
 Guarding the model without exposing the prompt:
   1. The builder system prompt lives only in the builder service (image or
      ConfigMap). The NVCF key comes from the same Vault secret.
   2. Narrow API, data only:
        POST /builder/session                       -> builder session id
        POST /builder/turn {session_id, user_message} -> {reply, draft_config}
      Conversation history is kept server-side, so the client cannot inject
      system/assistant turns or rewrite history.
   3. The service fixes model, system prompt, temperature, max_tokens,
      reasoning_effort; client values are ignored.
   4. Structured output only: response_format json_schema (enforced by the NIM's
      vLLM). Schema = short reply + draft-config fields; models, voices, tools,
      languages are enums built from the deployment catalog. Reasoning text is
      stripped, never returned.
   5. Output validation: schema + catalog check, length caps on free-text fields
      (persona, domain), reject replies that echo the system prompt (overlap
      check).
   6. Input guards: message length and turn caps; rate limit per IP and session
      (nginx limit_req + service). Refusal rules (off-topic, opinions, harmful,
      profane or illegal personas) in the system prompt, re-checked on the final
      config. Optional later: a content-safety NIM (costs a function + GPU);
      add only if testing shows gaps.
   7. Audit log of builder session ids and refusals (no user content unless
      wanted).
